## 1. 真机用了一圈之后的评价（产品视角）

装到魅族 21（Android 16）上用了半天，作为用户我最强的感受是：**功能密度极高，但发现性极差。**

| 观察 | 说明 |
| :--- | :--- |
| 首页信息密度合理 | 服务 / 快捷手势 / 特色功能三段式，比很多工具类 App 清晰 |
| **671 个设置键** | 这是真实数字（`SettingsPreferenceKeys` 671 个 `PreferencesKey`）。用户不可能浏览完 |
| 功能藏在三层下 | 「触钮集合 → 某侧 → 某个手势 → 动作」，想改一个动作要点 4 次 |
| 缺"从场景找功能"的入口 | 只有"从功能找设置"，没有"我想做 X，该开哪个" |
| 新用户无引导 | 首启后不知道悬浮球/手势/面板能干什么，只能自己试 |

**产品建议（按 ROI 排序）：**

1. **给设置加"搜索 + 常用"**：671 个键里 80% 的人只改 10 个。把"最近改过的 5 个"和全局搜索放在设置顶部，成本 2 天，体验提升最大。
2. **场景化预设**（不是功能列表）：如"单手操作"/"阅读"/"游戏防误触"/"快速取词"四个一键预设，本质是批量改设置。成本 3–5 天。
3. **首启 3 步引导**：只教"边缘滑出触钮""悬浮球长按取词""面板在哪"，其余让人自然发现。成本 1–2 天。

## 2. 代码视角：真正的强项（不是客套）

| 强项 | 证据 |
| :--- | :--- |
| **注释写"为什么"且带证据** | 浮层注释里直接贴 logcat 调用栈、ROM 型号、性能采样值。这是踩过坑才写得出的。 |
| **运行时防御成体系** | 浮层租约 + 代次 + 看门狗 + IME 合并 + 熄屏重建确认（`CHROME_REBUILD_CONFIRM_MS`），覆盖了国产 ROM 的常见异常 |
| **把设置写入当性能问题** | 单快照 + 切片派生 + `shareIn(WhileSubscribed)`，还知道"`settings` 必须保持冷流"这种反直觉取舍 |
| **国际化工程化** | 4,936 条 × 5 语言 + 硬编码中文守卫脚本，个人项目里几乎见不到 |
| **引擎与 APK 解耦** | 引擎包在 `filesDir`，Full→Lite 覆盖不丢，更新链路永远发 Lite——这是想清楚了的架构决策，不是偷懒 |
| **发版流水线产品级** | 构建 + 翻译检查 + lint + 签名 + `update.json` 全自动 |

## 3. 结构视角：这次亲手改才看清的三件事

### 3.1 真正的债是"单例即架构"，不是"模块不够多"

实测：`overlay/` 根目录 129 个文件里，`FloatBallOverlay` 被引用 **267 次**、`FloatBallLayout` 93 次、`OverlayManager` 53 次。
**任何单个文件搬走，平均连锁 2–5 个未定义符号。**

这意味着：模块化（加 `:feature:overlay-panels`）能改善**组织**，但改不了**耦合**。
耦合的根在"一个 object 管 6 件事 + 谁都能静态拿到它"。

**这次做对的事**：把 `FloatBallOverlay` 4,302 → 3,313 行，拆出 10 个职责类（截图抑制、位置预览、外观预览、销毁、创建、空闲动画、触摸窗口、拖拽布局、拖拽收尾、生命周期）。
**这是本次唯一"结构真的变好"的部分**，比搬 8.6 万行更有价值。

### 3.2 两套架构并存的真实风险

面板现在通过 `PanelRuntimeHooks` 的 **121 个 `@Volatile var` 槽位**反向调用 `:app`。
这套机制让迁移得以进行，但它同时意味着：

- 依赖关系是隐式的（编译器看不见"面板需要 app 的什么"）
- 生命周期靠人脑（谁在什么时候赋值？忘了赋值就是静默 null）
- 测试无法替换实现

**如果不加约束，三年后新人和 AI 都会写出第三套写法。** 因此我在 `AGENTS.md` 里加了硬规则：
钩子数只许减不许增（121）、新代码禁止新增、零引用即删、季度盘点。

### 3.3 17 个 >1500 行的文件是"下一批债"

```
3313  FloatBallOverlay            （已拆过一轮，剩余是交互状态机）
2558  HistoryPanelScreen
2284  FileBrowserPanel
2177  ScreenPinManager
2128  QuickMenuToolScreens
2004  OverlaySettingsMutator      （671 个设置键的家）
1994  ThinActionIcons
1956  SearchPanelScreen
```

这些文件里，`ScreenPinManager`（2,177 行）和 `OverlaySettingsMutator`（2,004 行）是最该拆的两个：
一个管窗口 + 状态 + 权限，一个管 671 个键的读写。

## 4. 我这次判断错的三个地方（重要，供你校准我的建议）

| 我原来说的 | 实测结论 |
| :--- | :--- |
| "39 个 trampoline Activity 拖慢冷启动" | **错**。跳板不参与启动，只在被调用时实例化。冷启动收益≈0，合并只值得为可维护性做 |
| "阶段 C 收完根目录 220 个文件，`:app` 就能到 20 万行" | **不成立**。引用密度决定搬不动；真要搬得先做宿主接口化 |
| "拆出的类可以立即补大量单测" | **多数不行**。10 个类里 9 个依赖单例状态/Looper，需要先做状态对象化 |

**教训**：给这类项目做评审，"行数/文件数"是最容易骗人的指标，**引用密度和依赖方向**才是真指标。

### P2 —— 半年内（可选）

| # | 事项 | 说明 |
| :-- | :--- | :--- |
| 9 | 宿主服务接口化（`FloatBallPort` / `OverlayPort`） | 阶段 C 的前置；不接口化就别搬文件 |

### 明确不建议做的

- ❌ 为"`:app` ≤ 20 万行"这个指标重构
- ❌ 继续合并 trampoline（冷启动收益≈0）
- ❌ 一次性给 overlay 补大量单测（先状态对象化）

**危险区域（改之前先想清楚）：**

- `FloatBallOverlay` 剩余 3,313 行：触摸事件状态机，`dragSession`/`cursorPreview*`/`regionalPick*` 十几个状态互咬
- `PanelRuntimeHooks` 121 个槽位：改一个要同时看面板侧与 app 侧赋值时机
- `SettingsPreferencesEditor.snapshotFlow`：`settings` 必须保持冷流，改成热流会破坏 30+ 处"写后立刻读"

**安全区域（可以放心改）：**

- 已拆出的 10 个 `FloatBall*` 职责类（各自 <350 行，职责单一）
- `:feature:overlay-panels` 里的面板（与 `:app` 只通过钩子单向通信）
- 任意 `core:*` 模块

## 8. 最后一句

**这个项目最稀缺的不是技术，是"把为什么写下来"的习惯。**
它现在缺的也不是更多功能，而是**让第二个人（或半年后的你）能在 10 分钟内安全改动一处设置/一个手势的路径**。

结构重构做到 7.7 分就够了——**继续追分数会伤害产品**。把力气花在"设置可达性"和"首启引导"上，用户感知的提升会远大于再搬 5 万行代码。
